Omnirig + Kenwood TS-590 — VFO B Death Loop

Symptom. With Omnirig connected to a Kenwood TS-590, only VFO A is usable. Selecting VFO B (from software or the front panel) causes the radio to oscillate between A and B every poll cycle. Front-panel input is overridden faster than it can be applied. Killing Omnirig restores normal operation.

Diagnosis. The shipped Omnirig .ini for the TS-590 family either (a) misparses the IF; status response when the receive VFO is B, or (b) issues an unconditional FR0;/FT0; write inside its STATUS poll block. Either causes Omnirig to slam the rig back to VFO A on every poll (every 100–500 ms). This is the well-known cause of the symptom and is reproducible on both the original TS-590S and the TS-590SG with the wrong .ini selected.

2. Quick orientation: which radio do you have?

The two variants take different .ini files because the SG changed several CAT response semantics:

  • TS-590S (original, 2010, discontinued). Use TS-590S.ini. Latest firmware: 2.05.
  • TS-590SG (2014). Use TS-590SG.ini. Latest firmware: 1.07.

To check firmware without Omnirig running:

  1. Power the radio off.
  2. Hold A=B while pressing POWER.
  3. The display shows the firmware version. Release the keys.

3. CLI troubleshooting (PowerShell 7+)

3.1 Locate the Omnirig install and inspect rig profiles

# Find the Omnirig install (default is under Program Files (x86)\Afreet)
Get-ChildItem 'C:\Program Files (x86)\Afreet','C:\Program Files\Afreet' -Recurse -Filter 'OmniRig.exe' -ErrorAction SilentlyContinue |
    Select-Object FullName, @{n='Version';e={ (Get-Item $_.FullName).VersionInfo.FileVersion }}

# List installed rig profiles
$rigsDir = 'C:\Program Files (x86)\Afreet\OmniRig\Rigs'
Get-ChildItem $rigsDir -Filter 'TS-590*.ini' | Select-Object FullName, Length, LastWriteTime

3.2 Back up the existing profile before any edit

$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
Copy-Item "$rigsDir\TS-590S.ini"  "$rigsDir\TS-590S.ini.$stamp.bak"  -ErrorAction SilentlyContinue
Copy-Item "$rigsDir\TS-590SG.ini" "$rigsDir\TS-590SG.ini.$stamp.bak" -ErrorAction SilentlyContinue
Get-ChildItem $rigsDir -Filter 'TS-590*' | Format-Table Name, Length, LastWriteTime

3.3 Search the profile for the two known offending patterns

# (a) STATUS blocks that *write* FR/FT (this is the death-loop trigger)
Select-String -Path "$rigsDir\TS-590*.ini" -Pattern '^\s*Command\s*=\s*FR[01];|^\s*Command\s*=\s*FT[01];' -Context 4,2

# (b) Validation masks that assume IF; byte 30 (RX VFO) == '0'
Select-String -Path "$rigsDir\TS-590*.ini" -Pattern 'Validation' -Context 1,4
Bad pattern (do NOT keep in any STATUS block): 
[STATUS1]
Command=IF;FR0;FT0;
ReplyLength=38
Validation=...
The trailing FR0;FT0; rewrites the radio to VFO A on every poll. It belongs only in explicit user-action WRITE blocks ([pmVfoA], [pmVfoAA], etc.), never in [STATUS*].

3.4 Verify the COM port is reachable independently of Omnirig

# List COM ports
[System.IO.Ports.SerialPort]::GetPortNames() | Sort-Object

# Open the port at the radio's configured rate (Menu 62 on 590S, Menu 77 on 590SG)
# Common settings: 115200,N,8,1 over USB; or whatever you set on the rear DB9.
$port = New-Object System.IO.Ports.SerialPort 'COM5',115200,'None',8,'One'
$port.NewLine = ';'
$port.ReadTimeout = 1500
$port.Open()
try {
    $port.WriteLine('FA')      # query VFO A frequency
    Start-Sleep -Milliseconds 200
    $port.ReadExisting()       # should return e.g. 'FA00014250000;'
    $port.WriteLine('IF')      # full status
    Start-Sleep -Milliseconds 200
    $port.ReadExisting()
} finally {
    $port.Close()
}

The byte at offset 30 (1-based) of the IF; response is the receive VFO indicator: 0 = VFO A, 1 = VFO B. Switch the radio to VFO B from the front panel (with Omnirig closed!) and re-issue IF;; the indicator must change. If it does not, the radio is reporting incorrectly and a firmware update is in order.

3.5 Check the Omnirig settings persisted in the registry

# Omnirig 1.x stores per-rig settings here
Get-ItemProperty 'HKCU:\Software\Afreet\OmniRig\RIG1','HKCU:\Software\Afreet\OmniRig\RIG2' -ErrorAction SilentlyContinue |
    Format-List RigType, Port, Baud, Poll, Timeout, Dtr, Rts

3.6 Tail the Omnirig debug log while reproducing

Omnirig 2.x writes to %LOCALAPPDATA%\Afreet\OmniRig2. Enable logging via the tray-icon menu (Settings → Log) then:

Get-ChildItem "$env:LOCALAPPDATA\Afreet" -Recurse -Filter '*.log' | Sort-Object LastWriteTime -Descending | Select-Object -First 3
Get-Content "$env:LOCALAPPDATA\Afreet\OmniRig2\OmniRig.log" -Wait -Tail 50

Watch the trace as you press A/B on the rig. A correctly-behaved log shows one IF; per poll and no FR/FT writes unless you initiate a VFO change in software. A failing log shows FR0; emitted on every poll cycle.

4. Editing the .ini safely

Open the chosen profile in a UTF-8-aware editor:

notepad "$rigsDir\TS-590SG.ini"
# or
code   "$rigsDir\TS-590SG.ini"

Three things to verify or change:

  1. Remove writes from STATUS. In every [STATUS…] section, the Command= line should contain only read commands (IF;, SM0;, FA;, FB;, MD;, etc.). If you see FR or FT there, comment the section out by prefixing each line with ; and add a corrected one.
  2. Validation mask must not pin RX VFO. Validation strings use a Mask/Flags pair of equal length. Bytes you don't care about must be 00 in the mask. The byte aligned to IF; offset 30 (RX VFO) should be 00 in any STATUS validation mask, or you'll fail validation the moment you go to VFO B.
  3. VFO write commands must use the right verbs.
    • FR0; — set RX to VFO A
    • FR1; — set RX to VFO B
    • FT0; / FT1; — set TX VFO
    These belong in [pmVfoA], [pmVfoB], [pmVfoAA], [pmVfoBB], [pmVfoAB], [pmVfoBA], [pmSplitOn], [pmSplitOff].

Reference: Kenwood "PC Control Command Reference" linked in section 1.

5. Settings to apply in Omnirig itself

SettingRecommended valueWhy
Rig typeTS-590S or TS-590SG exactly matching the radioMismatch is the single most common root cause of this symptom.
Poll int.500 msAnything < 250 ms turns minor mismatches into a runaway loop.
Timeout4000 msTolerate occasional radio busy without forcing a re-init.
PortEither the rear DB-9 or the USB virtual COM — not bothMixing the two ports causes identical-looking symptoms.
DTR / RTSBoth OFF (or per radio menu)The TS-590 doesn't need handshake. Leaving lines asserted can confuse some USB-serial bridges.

7. End-to-end fix and verify procedure

  1. Close every program touching CAT (logger, WSJT-X, fldigi, Hamlib, Omnirig client). 
    Get-Process | Where-Object { $_.ProcessName -match 'OmniRig|wsjtx|fldigi|N1MM|Log4OM|HRD|jtdx' } | Format-Table Id, ProcessName
  2. Confirm radio firmware is current (sections 1 and 2). Update if older than the table.
  3. Back up .ini profiles (section 3.2).
  4. Run the quick scan in section 3.3. If either pattern is present, replace the profile with a known-good community version or hand-edit per section 4.
  5. In Omnirig settings: confirm rig type, set Poll = 500 ms, Timeout = 4000 ms.
  6. Open Omnirig's built-in client only (no logger). Click Show. Verify frequency and mode track the front panel for VFO A.
  7. Press A/B on the radio to select VFO B. Expected: the Omnirig display follows to VFO B's frequency. No oscillation. Front-panel A/B button continues to work.
  8. Toggle split (RX A / TX B): Omnirig should report split state and the radio should remain stable.
  9. Tail the log (section 3.6) for one full minute and confirm zero FR/FT traffic during steady-state polling.
  10. Re-launch the logger / digital-mode software one at a time and re-test after each.
Pass criteria. All of the following hold for at least 5 minutes of continuous operation on each VFO:
  • Front-panel A/B selection persists.
  • Omnirig reads correct frequency on whichever VFO is active.
  • No FR0;/FR1;/FT0;/FT1; in the Omnirig log unless triggered by a deliberate user action.
  • Split engages and disengages cleanly from both ends.

8. If it still fails after a clean .ini

  1. Try the other Omnirig major version. Versions 1.x and 2.x have different polling state machines. On the TS-590 family, one usually works where the other doesn't on a given firmware revision. They install side by side.
  2. Reinstall. Uninstall Omnirig, delete %LOCALAPPDATA%\Afreet\OmniRig* and the Rigs\ folder, reinstall, then re-deploy your verified .ini.
  3. Cross-check with ARCP-590G. Kenwood's own control program speaks the radio directly — if VFO B works there but not under Omnirig, the radio and cable are exonerated and the problem is unambiguously Omnirig configuration.
  4. Bypass via Hamlib. If a logger only needs frequency/mode tracking (not Omnirig specifically), rigctld -m 2028 -r COM5 -s 115200 can substitute and is less aggressive about VFO writes. This is a workaround, not a fix.
  5. Open a ticket. Email VE3NEA (Alex Shovkoplyas) via the contact link on dxatlas.com. Attach: Omnirig version, exact .ini in use, radio firmware version, a 60-second debug log capturing the failure.
