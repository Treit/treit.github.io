Kenwood TS-590 OmniRig VFO B Loop Fix

A from-scratch setup and change report for fixing the HDSDR/OmniRig/Hamlib VFO B loop where a TS-590 beeps and flickers instead of sitting stably on VFO B.

Result: the stable fix is to keep OmniRig talking TS-2000 CAT over the virtual COM port, but replace stock rigctlcom with a tiny raw Kenwood CAT bridge that forwards status polls to rigctld using Hamlib's raw w command. This avoids Hamlib's target-VFO polling path, which was the source of the repeated VFO switching.

1. Summary

The failure was not a front-panel A/B problem in the radio. The failure was caused by the PC-side CAT bridge. In the broken configuration, OmniRig polls the rig by sending normal TS-2000 status commands such as IF;. Stock rigctlcom answers those TS-2000 commands by calling Hamlib VFO APIs. On a TS-590, those calls physically emit Kenwood FR0 and FR1 commands. After one switch to VFO B, the bridge keeps tugging the radio away from B and back again, producing the beep/flicker loop.

The replacement bridge does less, on purpose. It opens the radio side of the virtual COM pair, receives OmniRig's CAT commands, and forwards them to rigctld as raw Kenwood CAT with w IF;, w FA;, and similar. Raw reads do not ask Hamlib to retarget VFOs, so the radio can remain on VFO B without being poked every poll interval.

Item Final value
Radio Kenwood TS-590 through Hamlib model 2031
Real CAT port COM3 at 115200 baud on the tested station
Hamlib daemon rigctld on 127.0.0.1:4532
Virtual COM pair COM10 is the bridge/radio side; COM11 is the OmniRig/HDSDR side
OmniRig rig type TS-2000, not TS-590, because the OmniRig side is TS-2000-compatible CAT
Replacement bridge safe_ts590_omnirig_bridge.py

HDSDR

  v

  |
  v
TS-590 on COM3 at 115200 baud

The key design rule is: OmniRig can continue to believe it is talking to a TS-2000, but the bridge must not translate status reads through Hamlib's VFO-targeting APIs. It must forward raw Kenwood CAT reads instead.

3. From-scratch setup for Randy KC7AVA

3.1 Install prerequisites

  1. Install OmniRig and configure HDSDR to use OmniRig.
  2. Install Hamlib for Windows and note the path to rigctld.exe and rigctl.exe. The tested station used C:\tools\hamlib\hamlib-w64-4.7.1\bin.
  3. Install a virtual null-modem pair such as com0com. Create a pair equivalent to COM10 and COM11.
  4. Install Python 3 and pyserial: 
    python -m pip install pyserial
  5. Download safe_ts590_omnirig_bridge.py and save it as %USERPROFILE%\Apps\RigBridge\safe_ts590_omnirig_bridge.py.

3.2 Configure OmniRig

In OmniRig, configure RIG1 like this. Do not select TS-590 here when using this bridge path.

SettingValue
Rig typeTS-2000

Baud115200
RTSLow / disabled
DTRLow / disabled
Poll500 ms
Timeout4000 ms

The live OmniRig file is normally: 

%APPDATA%\Afreet\Products\OmniRig\OmniRig.ini

The relevant INI values should look like this: 

[RIG1]
RigType=TS-2000
Port=11
BaudRate=12
RtsMode=0
DtrMode=0
PollMs=500
TimeoutMs=4000

3.3 Start rigctld

Adjust COM3 if Randy's TS-590 appears on a different Windows COM port. 

C:\tools\hamlib\hamlib-w64-4.7.1\bin\rigctld.exe `
  -m 2031 `
  -r COM3 `
  -s 115200 `
  -t 4532 `
  -T 127.0.0.1 `
  -W 10 `
  -w 1

The -w 1 startup write delay is retained from the previous anti-click setup. The -W 10 twiddle timeout helps reduce VFO churn in some Hamlib paths, but it is not the root fix by itself.

3.4 Start the safe bridge

python %USERPROFILE%\Apps\RigBridge\safe_ts590_omnirig_bridge.py `
  --serial-port \\.\COM10 `
  --baud 115200 `
  --rigctld 127.0.0.1:4532 `
  --log %USERPROFILE%\safe-ts590-omnirig-bridge.log

3.5 Optional PowerShell helpers

These are the essential helper variables and start command. They can be adapted into %USERPROFILE%\Documents\PowerShell\Microsoft.PowerShell_profile.ps1. 

$script:HamlibBin = 'C:\tools\hamlib\hamlib-w64-4.7.1\bin'
$script:RigctldExe = Join-Path $script:HamlibBin 'rigctld.exe'
$script:RigctlExe = Join-Path $script:HamlibBin 'rigctl.exe'
$script:RigctldEndpoint = '127.0.0.1:4532'
$script:RigctldArgs = @(
    '-m', '2031',
    '-r', 'COM3',
    '-s', '115200',
    '-t', '4532',
    '-T', '127.0.0.1',
    '-W', '10',
    '-w', '1'
)
$script:SafeRigBridgeScriptPath = Join-Path $env:USERPROFILE 'Apps\RigBridge\safe_ts590_omnirig_bridge.py'
$script:SafeRigBridgeLogPath = Join-Path $env:USERPROFILE 'safe-ts590-omnirig-bridge.log'

function Start-Rigctld {
    Start-Process -FilePath $script:RigctldExe -ArgumentList $script:RigctldArgs -WindowStyle Minimized
}

function Start-RigBridge {
    Start-Process -FilePath 'python' `
        -ArgumentList @(
            $script:SafeRigBridgeScriptPath,
            '--serial-port', '\\.\COM10',
            '--baud', '115200',
            '--rigctld', $script:RigctldEndpoint,
            '--log', $script:SafeRigBridgeLogPath
        ) `
        -WindowStyle Minimized
}

  2. Start the safe bridge.

4. Red/green diff report

4.1 PowerShell: rigctld arguments

This change is retained, but it is not the main VFO B fix. It helps keep Hamlib from rapidly twiddling target VFOs in code paths that still use that behavior.

$script:RigctldArgs = @(
'-m', '2031',
'-r', 'COM3',
'-s', '115200',
'-t', '4532',
'-T', '127.0.0.1',
+ '-W', '10',
'-w', '1'
)

4.2 PowerShell: bridge process

This is the important change. Stock rigctlcom was replaced by the safe raw bridge.

function Start-RigBridge {
- Start-Process -FilePath $script:RigctlcomExe `
- -ArgumentList @(
- '-m', '2014',
- '-r', $script:RigctlcomRadioSide,
- '-s', "$script:RigctlcomBaud",
- '-t', '4532',
- '-T', '127.0.0.1'
- ) `
- -WindowStyle Minimized
+ Start-Process -FilePath 'python' `
+ -ArgumentList @(
+ $script:SafeRigBridgeScriptPath,
+ '--serial-port', $script:RigctlcomRadioSide,
+ '--baud', "$script:RigctlcomBaud",
+ '--rigctld', $script:RigctldEndpoint,
+ '--log', $script:SafeRigBridgeLogPath
+ ) `
+ -WindowStyle Minimized
}

4.3 PowerShell: stop old and new bridge processes

The stop helper now terminates the Python bridge and also cleans up any leftover legacy rigctlcom process so both bridges cannot fight over the COM pair.

function Stop-RigBridge {
- $oldRigctlcom = Get-Process -Name rigctlcom -ErrorAction SilentlyContinue
- if ($oldRigctlcom) { $oldRigctlcom | Stop-Process -Force }
+ $proc = Get-CimInstance Win32_Process |
+ Where-Object {
+ $_.Name -match '^(python.*|py)\.exe$' -and
+ $_.CommandLine -like "*$script:SafeRigBridgeScriptPath*"
+ }
+ if ($proc) { $proc | ForEach-Object { Stop-Process -Id $_.ProcessId -Force } }
+
+ $oldRigctlcom = Get-Process -Name rigctlcom -ErrorAction SilentlyContinue
+ if ($oldRigctlcom) { $oldRigctlcom | ForEach-Object { Stop-Process -Id $_.Id -Force } }
}

4.5 OmniRig TS-2000 rig profile overlay

An IF-only TS-2000 profile overlay was tested while isolating the problem. It comments out the FA; and FB; status polls. That overlay reduces traffic, but the final safe-bridge validation showed it is not required to fix VFO B. With the safe bridge and the original TS-2000 profile restored, IF;, FA;, and FB; reads all remained safe and produced zero FR0/FR1 or FT0/FT1 write commands.

5. Validation and minimal-change proof

5.1 Broken stock bridge reproduced the exact symptom

In the broken run, the only user action was to get to VFO B and wait. The stock bridge path then repeatedly moved the radio's receive VFO away from B and back to B.

Bad evidence: stock rigctlcom plus OmniRig polling produced repeated physical Kenwood FR0 and FR1 commands after the VFO B switch. 
rig_set_vfo called vfo=VFOA
kenwood_transaction called cmd=FR0
rig_set_vfo called vfo=VFOB
kenwood_transaction called cmd=FR1
rig_set_vfo called vfo=VFOA
kenwood_transaction called cmd=FR0
rig_set_vfo called vfo=VFOB
kenwood_transaction called cmd=FR1

The matching rigctlcom side showed OmniRig status polling, not a deliberate instruction from the operator to leave VFO B. That is why changing the front-panel behavior or simply starting from VFO A could not solve the issue.

5.2 -W 10 -w 1 alone was not enough

Adding Hamlib's twiddle timeout reduced some unwanted churn, but it still allowed unwanted VFO targeting in the stock bridge path. It is useful as a secondary mitigation, not a standalone fix.

5.3 Safe bridge with the original TS-2000 profile proved the minimal fix

To check whether the OmniRig profile overlay was actually required, the TS-2000 overlay was temporarily disabled and the stock TS-2000 profile was used with the safe raw bridge. After switching to VFO B, the bridge saw normal status reads and no VFO-write commands.

Minimal-change test: with the original TS-2000 profile, the safe bridge handled 22 IF; reads, 21 FA; reads, and 22 FB; reads, produced zero FR/FT write commands, and the radio remained on VFOB. 
IF        : 22
FA        : 21
FB        : 22
FRFT      : 0
FinalVfo  : VFOB

6. Alternative implementations that avoid Python

Option Would it work? Pros Cons Recommendation
C executable Yes Small single EXE, no runtime dependency, direct Win32 serial and Winsock APIs. More code for buffering, timeouts, error handling, installer/signing, and logging. Easier to introduce memory or handle-lifetime bugs. Good if this becomes a packaged utility for multiple shacks.
Rust executable Yes Single EXE, memory safe, good serial/TCP crates, easier robust parsing than C. Requires Rust toolchain to build; slightly larger binary; still needs release packaging. Best compiled replacement if we want to move beyond Python later.
PowerShell bridge Possible No separate compiled language; can use System.IO.Ports.SerialPort and System.Net.Sockets.TcpClient. Less ideal for continuous low-latency serial IO. Buffering, event callbacks, process lifetime, and clean shutdown are more fragile. It is also easier for the bridge to be disrupted by profile reloads or console state. Acceptable for a quick proof of concept, not preferred for the always-on bridge.
Python bridge Already works Very small, readable, easy to modify at the station, good enough performance for 500 ms OmniRig polling. Requires Python and pyserial. Keep this for now unless packaging or deployment friction becomes a real issue.

The important implementation detail is independent of language: the bridge should forward raw Kenwood CAT reads to rigctld with the raw w command and should not answer OmniRig status polls by calling Hamlib target-VFO APIs.

7. Troubleshooting checklist

If VFO B still loops

  1. Make sure rigctlcom.exe is not running. Only the safe bridge should own COM10.
  2. Confirm OmniRig is on TS-2000, COM11, 115200 baud.
  3. Confirm the safe bridge log shows Starting safe TS-590 OmniRig bridge.
  4. Confirm the safe bridge log does not show repeated CAT FR0;, CAT FR1;, CAT FT0;, or CAT FT1;.
  5. Confirm rigctld is controlling the real TS-590 port, not the virtual COM pair.
  6. Confirm the virtual pair is crossed correctly: OmniRig uses COM11, the safe bridge uses COM10.

Useful commands

taskkill /f /im rigctlcom.exe
